## Deep dive: applying the decision steps to real requirements

The five steps above are easiest to learn by applying them. Harbourline's integration backlog at the start of the project held ten requirements. @tbl:backlog shows where each one landed, and why. Read the "Why" column before the "Where" column: the reasoning matters more than the answer, because your own requirements will differ in detail.

::: {#tbl:backlog caption="Ten Harbourline requirements and where they were built"}
| # | Requirement | Where | Why |
|---|---|---|---|
| 1 | Reject a lease whose end date is before its start date | Business rule or plug-in | Must block the save; a function can't roll it back |
| 2 | Show the tenant's credit status on the lease form | Virtual table or embedded call | Reading live data that LedgerOne owns; no copy needed |
| 3 | Notify the property manager when a lease is signed | Power Automate | Low volume, owned by the lettings team, no code |
| 4 | Send every new or changed customer to LedgerOne | Function (Service Bus trigger) | Must survive LedgerOne outages; retries, ordering and volume |
| 5 | Import 400 property listings from partners every night | Function (Blob trigger) | Large files, row-level validation, streaming |
| 6 | Give partners a REST API to search properties | Function behind API Management | External callers, versioning, throttling, keys |
| 7 | Load 2 million historical meter readings once | Function or console tool using bulk APIs | One-off volume; resumable checkpoints |
| 8 | Run a lease signing that waits days for a signature | Durable Functions | Long waits, timers and external events, with state |
| 9 | Export a month of invoices to Excel for finance | Function (HTTP) | File generation with a library; no licence cost |
| 10 | Let a maker add a "send reminder" button to an app | Custom connector over a function | Makers keep ownership of the app; developers own the API |
:::

Three patterns appear in the table. First, **nothing that must block a save** went to Functions (row 1); that belongs in the Dataverse transaction. Second, **ownership** often decides between Power Automate and code (rows 3 and 10): the lettings team can change a flow on Tuesday afternoon without a release, but they can't change a function. Third, the requirements that went to Functions share **at least one engineering need** that low-code handles badly: guaranteed delivery, volume, streaming, a public contract or long-running state.

### Cost of ownership, not only cost of running

Running costs for event-driven functions at Harbourline's volumes are usually small compared with the people costs around them. When you compare options, list what each one needs over three years:

- **Build**: who writes it, and do they know the tool?
- **Change**: how is a change tested and released? Who approves it?
- **Operate**: who is woken at 2 a.m. when it fails, and what do they look at?
- **Licence**: does it need premium connectors, extra capacity or a paid library?

A flow that a business analyst can change in an hour may be cheaper than a function that needs a developer and a pipeline, even if the function costs less to run. The reverse is also true: a flow with forty actions, three nested loops and no tests is an unowned program.

### Signals that a choice was wrong

Decisions age. Revisit one when you see any of these signs:

- A flow has grown loops, retries and error branches that nobody dares to edit.
- A plug-in calls an external HTTP endpoint and occasionally times out the user's save.
- A function contains business rules that the business wants to change every month.
- Two integrations write the same column and "fight" (Chapter 21 shows how to stop that).

::: tip
Keep the decision record from Step 5 next to the code. When someone proposes moving a requirement, the record shows what was considered last time, and saves the same debate.
:::

## Guided lab: explore the companion solution

This lab gets the companion code onto your machine and shows you around it, before Chapter 3 sets up the full environment. It needs only Git and the .NET 10 SDK, and takes about 20 minutes.

### Lab 1.1 – Clone and build

```bash
git clone https://github.com/vikashkumar669/AzureFunctions.git
cd AzureFunctions
dotnet --version
dotnet build HarbourlineConnect.slnx
```

**Expected output** (abridged and illustrative; versions and timings will differ):

```text
10.0.xxx
  Harbourline.Connect.Contracts succeeded → src/Harbourline.Connect.Contracts/bin/Debug/net10.0/…
  Harbourline.Connect.Core succeeded → src/Harbourline.Connect.Core/bin/Debug/net10.0/…
  Harbourline.Connect.Functions succeeded → src/Harbourline.Connect.Functions/bin/Debug/net10.0/…
  Harbourline.Connect.UnitTests succeeded → tests/Harbourline.Connect.UnitTests/bin/Debug/net10.0/…
Build succeeded in 41.2s
```

**Checkpoint:** the build ends with *Build succeeded* and no errors. If `dotnet --version` shows an older major version, install the .NET 10 SDK; the repository's `global.json` pins the SDK family.

### Lab 1.2 – Run the unit tests

```bash
dotnet test HarbourlineConnect.slnx
```

The tests need no Azure resources. **Checkpoint:** every test passes. The summary line reports a total and zero failures; the exact wording depends on the SDK and test platform version.

### Lab 1.3 – Find each requirement in the code

Use @tbl:backlog as a map. For each row built as a function, find the folder that implements it:

| Requirement | Folder |
|---|---|
| 4 – customers to LedgerOne | `src/Harbourline.Connect.Functions/Messaging/` |
| 5 – nightly feed import | `src/Harbourline.Connect.Functions/Feeds/` |
| 6 – partner search API | `src/Harbourline.Connect.Functions/Search/` |
| 8 – lease signing | `src/Harbourline.Connect.Functions/Leases/` |
| 9 – invoice export | `src/Harbourline.Connect.Functions/Excel/` |

Open one function file in each folder. Notice how short the functions are: each one reads its input, calls a service in `Harbourline.Connect.Core`, and maps the result. That split, thin functions over testable services, is the main design idea of the companion code, and Chapter 2 explains it.

### Lab 1.4 – Write your own decision record

Pick one integration from your own work (or invent one) and write a decision record in five lines, one per step of this chapter: *must it block the save? can we avoid a copy? who owns it? what is orchestration and what is code? where is it built?*

**Checkpoint:** someone who wasn't in the room can read your record and understand the choice without asking you.
