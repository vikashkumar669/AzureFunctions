## Deep dive: what is inside a token, and who decides

Authentication problems are much easier to solve once you can read a token. An access token from Microsoft Entra ID is a signed JSON Web Token (JWT): three Base64URL-encoded parts separated by dots. The middle part, the **payload**, holds the claims that Dataverse (or any other API) uses to decide who is calling and whether to accept the call.

### The claims that matter for integrations

::: {#tbl:claims caption="Token claims you will check most often"}
| Claim | Meaning | What goes wrong when it's wrong |
|---|---|---|
| `aud` | Audience: the API the token is for | A token for Microsoft Graph sent to Dataverse is rejected with 401 |
| `iss` | Issuer: the tenant that issued the token | A token from another tenant is rejected |
| `oid` | Object ID of the user or service principal | Dataverse looks up the user or application user by this identity |
| `appid` / `azp` | Client application that requested the token | Used by APIs that allow only listed clients (Chapter 14) |
| `roles` | App roles granted to the caller | Your own APIs authorize on these (Chapter 14) |
| `scp` | Delegated scopes, for user tokens only | Absent from app-only tokens |
| `exp`, `nbf` | Valid until / not before (Unix time) | Clock skew or caching an expired token causes 401s |
:::

Two families of tokens appear in this book. **Delegated** tokens (yours, from the Azure CLI or Visual Studio) carry `scp` and act as a person. **App-only** tokens (a managed identity's) carry no `scp`; they may carry `roles`. Dataverse accepts both, maps the identity to a user or an application user, and then applies that user's security roles. Authentication says *who*; Dataverse security roles say *what*.

### The scope string

The client factory in Step 1 asks for a token with the scope `https://<org>.crm11.dynamics.com/.default`. The `/.default` suffix means "whatever permissions this identity already has for that resource". For Dataverse there is nothing extra to grant in Entra ID: the application user and its roles in the environment are what matter. That's why a managed identity can call Dataverse without any API permission being added to it, but gets "user is not a member of the organization" until the application user exists.

### How DefaultAzureCredential decides

`DefaultAzureCredential` tries a chain of credentials in order and uses the first one that returns a token. Broadly, it tries **environment-based** credentials first, then **workload and managed identity**, then **developer tools** such as Visual Studio and the Azure CLI. On your laptop no managed identity exists, so your developer sign-in wins; in Azure the managed identity answers first. That's what lets the same code run in both places.

The chain has a cost: every failed attempt takes time, and an unexpected credential can win (for example, stale environment variables on a build agent). Two habits avoid surprises:

- In production, prefer a **specific** credential. A `ManagedIdentityCredential` (with a client ID for a user-assigned identity) can't silently pick another identity.
- Log which identity you're running as at start-up, using the `oid` from a test token or Dataverse's `WhoAmI`. A single log line saves hours.

::: security
Never log a whole token. Log claims you need for diagnosis (`oid`, `appid`, `aud`), never the encoded token, which can be replayed until it expires.
:::

### When a secret can't be avoided

Some partners only offer API keys or client secrets. Chapter 5's Step 5 keeps them in Key Vault, read through a Key Vault reference. Three more rules apply to every unavoidable secret: give each one an **owner** and an **expiry date**, rotate it on a schedule rather than after an incident, and alert before it expires. A secret nobody owns is an outage waiting for its expiry date.

## Guided lab: follow an identity from token to Dataverse user

**Requires:** your development environment, the Azure CLI signed in, and `jq` (any recent version). Optional: a deployed Function App with its managed identity turned on (Step 2).

### Lab 5.1 – Decode your own token

```bash
ORG=https://<your-dev-org>.crm11.dynamics.com
TOKEN=$(az account get-access-token --resource $ORG --query accessToken -o tsv)

# Decode the payload (second part); pad the Base64URL text first.
P=$(echo "$TOKEN" | cut -d. -f2 | tr '_-' '/+')
while [ $(( ${#P} % 4 )) -ne 0 ]; do P="$P="; done
echo "$P" | base64 -d | jq '{aud, iss, oid, appid, scp, exp}'
```

**Expected output** (illustrative; values are yours):

```json
{
  "aud": "https://<your-dev-org>.crm11.dynamics.com",
  "iss": "https://sts.windows.net/<tenant-id>/",
  "oid": "8e2a…",
  "appid": "04b07795-8ddb-461a-bbee-02f9e1bf7b46",
  "scp": "user_impersonation",
  "exp": 1793096411
}
```

**Checkpoint:** `aud` is your environment URL and `scp` is present, because this is a delegated token. The `appid` is the Azure CLI's own client application. Convert `exp` with `date -d @<exp>` to see when the token expires.

### Lab 5.2 – Run the probe as yourself

```bash
dotnet run --project samples/Harbourline.Probe
```

The probe uses `DefaultAzureCredential`, so on your laptop it runs as your CLI or Visual Studio sign-in. **Checkpoint:** the three query blocks from Chapter 4 print rows. If you see an authentication error, run `az login` again and check that your account is a user of the environment.

### Lab 5.3 – Find the managed identity's IDs (Azure)

If you've deployed the Function App, look up its identity:

```bash
PRINCIPAL=$(az functionapp identity show -g <resource-group> -n <app-name> \
  --query principalId -o tsv)
APPID=$(az ad sp show --id $PRINCIPAL --query appId -o tsv)
echo "object id: $PRINCIPAL"; echo "client id: $APPID"
```

**Checkpoint:** two different GUIDs. The **object ID** identifies the service principal; the **client (application) ID** is what you choose when you create the application user in the Power Platform admin center.

### Lab 5.4 – Confirm the application user in Dataverse

Use your own token from Lab 5.1 to look for the application user:

```bash
curl -s -G "$ORG/api/data/v9.2/systemusers" \
  -H "Authorization: Bearer $TOKEN" -H "Accept: application/json" \
  --data-urlencode '$select=fullname,applicationid,isdisabled' \
  --data-urlencode "\$filter=applicationid eq $APPID"
```

**Expected output** (illustrative):

```json
{ "value": [ { "fullname": "hlconnect-dev", "applicationid": "5c1e…",
               "isdisabled": false, "systemuserid": "…" } ] }
```

**Checkpoint:** exactly one row, not disabled. An empty `value` array means Step 3 hasn't been done in **this** environment; application users are per environment.

### Lab 5.5 – Check the role assignment

Expand the user's roles in the same request:

```bash
curl -s -G "$ORG/api/data/v9.2/systemusers" \
  -H "Authorization: Bearer $TOKEN" -H "Accept: application/json" \
  --data-urlencode '$select=fullname' \
  --data-urlencode '$expand=systemuserroles_association($select=name)' \
  --data-urlencode "\$filter=applicationid eq $APPID"
```

**Checkpoint:** `Harbourline Integration` is listed, and **System Administrator is not**. If you find System Administrator, remove it now; Step 4 explains why least privilege matters even in development.
