## Deep dive: sizing a Flex Consumption app

"Serverless" doesn't mean "no capacity planning". On Flex Consumption you choose a few numbers, and the platform does the rest. Knowing what each number controls lets you predict how your app will behave under load, and how hard it will push Dataverse.

### The four settings that matter

::: {#tbl:sizing caption="Flex Consumption settings that shape capacity"}
| Setting | What it controls | Default or range |
|---|---|---|
| Instance memory | Memory and CPU of every instance | 512 MB, 2,048 MB (recommended default) or 4,096 MB |
| HTTP concurrency | Requests one instance handles at once | Depends on instance memory: 4, 16 or 32 |
| Maximum instance count | Ceiling on on-demand instances, per scale group | Up to 1,000 |
| Always ready | Instances kept warm for a group or function | 0 unless you set it |
:::

Two details are easy to miss. First, Flex Consumption **scales per function**: all HTTP functions scale together as one group, Event Grid–based Blob triggers form a second group, and Durable Functions triggers a third. Every other function, such as each Service Bus or timer trigger, scales on its own instances. Second, the maximum instance count applies **to each group separately**, not to the app as a whole. An app with an HTTP group and two Service Bus functions can therefore run more instances in total than its maximum suggests.

### Worked example: the partner search API

Harbourline expects up to 120 partner searches in flight at peak. With 2,048-MB instances and the default HTTP concurrency of 16, the HTTP group needs about 120 ÷ 16 = 8 instances. A maximum instance count of 20 leaves headroom; two always-ready instances remove most cold starts during office hours.

Now look at it from Dataverse's side. If each search makes two Dataverse calls, peak load is roughly 240 calls in flight, all from one application user. Chapter 15 explains Dataverse's service protection limits, which count requests and concurrent requests **per user per web server**. The point here is the arithmetic:

> concurrent Dataverse calls ≈ instances × concurrency per instance × calls per execution

Every factor in that formula is under your control. When a downstream system can't take the load, lower the maximum instance count or the concurrency, rather than hoping the retries work out.

### Cold starts and always ready

A **cold start** happens when the platform must start a new instance and load your app before running the function. For HTTP APIs used by people, an occasional slow first request is visible; for a queue consumer it rarely matters. Always-ready instances keep a set number of instances running for a group, and they are billed while they wait. Use them for user-facing HTTP groups, not for back-office triggers.

### Quotas above your app

Each subscription has a regional memory quota shared by all Flex Consumption apps; at the time of writing the default is 250 cores (512,000 MB) per region. A 4,096-MB instance counts as two cores. If several teams share a subscription, one app's scale-out can be limited by the others. Check the quota before a large load test (Chapter 23), and request an increase if needed.

::: warning
Don't design against exact scale-out rates. The platform adds instances quickly at first and more gradually as an app grows, and Microsoft may tune that curve. Design for the pattern, and measure your own app.
:::

## Guided lab: watch triggers and scaling settings

**Requires:** the tools from Chapter 3 (Core Tools, Azurite). If you haven't set them up yet, do Chapter 3 first and come back.

### Lab 2.1 – Run the trigger gallery locally

The sample project `samples/Harbourline.Samples.Triggers` contains the four trigger examples from this chapter. Start Azurite in one terminal, then run the gallery in another:

```bash
azurite --silent --location ./.azurite
cd samples/Harbourline.Samples.Triggers
func start
```

**Expected output** (abridged and illustrative):

```text
Functions:

        RequestLeaseSignature: [POST] http://localhost:7071/api/leases/{leaseId:guid}/signature

        NightlyInvoiceSync: timerTrigger
        OnOrderSubmitted: serviceBusTrigger
        OnPropertyFileArrived: blobTrigger
```

The Service Bus and Blob functions may log connection warnings because no namespace or Event Grid subscription exists locally. That's expected: the host still starts, and the HTTP and timer functions work.

**Checkpoint:** you see all four functions listed with their trigger types.

### Lab 2.2 – Run a timer function on demand

You don't need to wait until 02:00. The host's admin endpoint runs a non-HTTP function immediately. Locally, no key is needed:

```bash
curl -i -X POST http://localhost:7071/admin/functions/NightlyInvoiceSync \
     -H "Content-Type: application/json" -d '{ "input": "" }'
```

**Expected result:** `HTTP/1.1 202 Accepted`, and the host log shows an *Executing* line followed by *Executed … (Succeeded)* for `NightlyInvoiceSync`.

In Azure, the same endpoint needs the app's master key in an `x-functions-key` header. Treat that key like a password; Chapter 14 explains why most callers should never hold it.

### Lab 2.4 – Read the scale settings of a deployed app (optional)

If you already have a Flex Consumption app, the Azure CLI shows and changes its scale settings:

```bash
az functionapp scale config show -g <resource-group> -n <app-name>

# Example change: two always-ready instances for the HTTP group
az functionapp scale config always-ready set -g <resource-group> -n <app-name> \
  --settings http=2
```

The first command lists the instance memory, the maximum instance count, any always-ready settings and any trigger concurrency you set. Compare them with your worksheet. Remember that always-ready instances are billed while they wait; remove them with `az functionapp scale config always-ready delete` when the lab is done.
