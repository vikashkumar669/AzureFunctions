## Deep dive: where configuration comes from

Every function in this book reads settings: a Dataverse URL, a partner's base address, a schedule. The same code runs on your laptop and in Azure, so it's worth knowing exactly how a value reaches your code in each place.

### One model, two sources

In the isolated worker, settings arrive as **environment variables**. Locally, Core Tools reads the `Values` section of `local.settings.json` and sets each entry as an environment variable for the worker process. In Azure, each **app setting** of the Function App becomes an environment variable in the same way. Your code never reads `local.settings.json` directly, which is why the file is never deployed and never committed.

.NET configuration then maps names to sections. A double underscore in an environment variable name is the section separator, so `Dataverse__Url` is read as `Dataverse:Url` and binds to the `Url` property of the options class registered for the `Dataverse` section (Chapter 6, Step 2). Use double underscores in app settings, because a colon isn't allowed in setting names on Linux hosts.

::: {#tbl:configsources caption="How a setting reaches the code"}
| Where you run | Source | Example |
|---|---|---|
| Laptop | `local.settings.json` → environment variable | `"Dataverse__Url": "https://…"` |
| Azure | App setting → environment variable | `Dataverse__Url` in *Environment variables* |
| Azure, secret | App setting holding a Key Vault reference | `@Microsoft.KeyVault(SecretUri=https://…)` |
| CI tests | Environment variables set by the pipeline | `env:` block in the workflow |
:::

### Connections without secrets

Triggers and bindings find their service through a **connection name**. When the setting with that name holds a connection string, the extension uses the string. When it doesn't exist, the extension looks for settings that share the name as a prefix. For example, the setting `ServiceBus__fullyQualifiedNamespace` tells the Service Bus extension to connect to that namespace **with an identity** instead of a key. Locally the identity is your developer sign-in (through `DefaultAzureCredential`); in Azure it's the Function App's managed identity. Chapter 5 sets up the identity side; here, notice that the same setting name works in both places.

The host's own storage works the same way. `AzureWebJobsStorage` holds a connection string locally (`UseDevelopmentStorage=true`, which points at Azurite). In Azure, the Bicep template in `infra/main.bicep` uses identity-based settings instead, so no storage key appears anywhere.

### What not to put in settings

- **Secrets in plain text** in Azure app settings. Use Key Vault references (Chapter 5, Step 5), so the secret lives in one audited place.
- **Values that must change together.** Two related timer schedules (Chapter 21) are safer as constants in code than as two settings someone might edit separately.
- **Large documents.** Settings are for small values. Put mapping tables or templates in Dataverse or Blob Storage.

::: tip
The companion code validates its settings at start-up (Chapter 6). A missing `Dataverse__Url` stops the host with a clear message instead of failing on the first request. Do the same in your own projects; it turns a 2 a.m. incident into a failed deployment.
:::

### The emulators, and their limits

Azurite emulates Blob, Queue and Table storage well enough for development. The Durable Task Scheduler emulator runs the same scheduler protocol as the cloud service, with its dashboard on port 8082. Neither emulator reproduces cloud behaviour exactly: performance, throttling and identity are different. Service Bus has its own emulator too, but this book connects development work to a real namespace, because Dataverse's service endpoint can only post to a namespace in Azure. Treat emulators as tools for fast feedback, and keep a real development environment in Azure for anything that involves Dataverse.

## Guided lab: check your environment end to end

This lab is a repeatable checklist. Run it now, and again whenever a new team member joins or a tool is upgraded. Each step names what you should see; if you see something else, the *Common errors* table above has the usual fixes.

### Lab 3.1 – Tool versions

```bash
dotnet --list-sdks
func --version
az version --query '"azure-cli"'
azurite --version
docker --version
```

**Expected output** (illustrative; your patch numbers will differ):

```text
10.0.xxx [/usr/share/dotnet/sdk]
4.x.x
"2.x.x"
3.x.x
Docker version 2x.x.x, build xxxxxxx
```

**Checkpoint:** a .NET **10** SDK is listed, and Core Tools reports major version **4**.

### Lab 3.2 – Azure sign-in

```bash
az login
az account show --query "{name:name, user:user.name}" -o table
```

**Checkpoint:** the subscription you intend to use is shown. If you have several, select one with `az account set --subscription "<name or id>"`.

### Lab 3.3 – Local services

Start Azurite and the Durable Task Scheduler emulator, each in its own terminal:

```bash
azurite --silent --location ./.azurite
docker run --rm -p 8080:8080 -p 8082:8082 mcr.microsoft.com/dts/dts-emulator:latest
```

Open `http://localhost:8082` in a browser. **Checkpoint:** the scheduler dashboard loads and shows the `default` task hub (it may be empty).

### Lab 3.4 – Settings

Copy the sample settings and fill in your development organization:

```bash
cd src/Harbourline.Connect.Functions
cp local.settings.sample.json local.settings.json
```

Edit `Dataverse__Url` and `Dataverse__OrganizationId`. Leave the LedgerOne and SignBridge values pointing at the local mocks.

**Checkpoint:** `git status` does **not** list `local.settings.json`. The repository's `.gitignore` excludes it; if it appears, stop and fix that before going further.

### Lab 3.5 – The mocks and the app

Start the mock partner APIs, then the Functions host:

```bash
dotnet run --project samples/Harbourline.Mocks      # terminal 1, from the repo root
func start                                          # terminal 2, in src/Harbourline.Connect.Functions
```

Then call the health endpoint:

```bash
curl -s http://localhost:7071/api/health
```

**Expected output** (illustrative):

```json
{"service":"Harbourline Connect","version":"1.0.0.0","checkedAtUtc":"2026-10-27T09:20:11.4821937+00:00"}
```

**Checkpoint:** you get HTTP 200 and a JSON body with a service name, a version and a UTC time. The health endpoint deliberately doesn't call Dataverse, so it works before Chapter 5's identity set-up is complete.

### Lab 3.6 – Debug one request

Set a breakpoint in `HealthFunction.Run` (in `src/Harbourline.Connect.Functions/Functions/HealthFunction.cs`), start the app under the debugger as described in Step 8, and repeat the `curl` call.

**Checkpoint:** execution stops at your breakpoint, and the *Call Stack* window shows your function called from the worker's invocation pipeline, not from your own code. That pipeline, including the middleware from Chapter 18, runs before every function.

### Lab 3.7 – Clean up (optional)

Stop the host, the mocks and both emulators with Ctrl+C. Azurite's data stays in `./.azurite`; delete the folder to start fresh next time.
